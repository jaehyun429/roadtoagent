1. messages가 스텝마다 어떻게 자라는지 — 첫 호출엔 태스크 하나, 두 번째엔 태스크+도구호출+결과, 세 번째엔 그 위에 또… 이런 구조를 그림이나 예시로. 로그의 토큰 수(234→1479)가 증거입니다.
왜 쌓이는가? : 모델은 호출간 기억이 없어서 스텝마다 계속 점진적으로 쌓아올리면서 넘겨줌 -> 상태를 계속 저장하면서 넘겨줌
첫 호출엔 유저 태스크가 쌓이고, 두번째 호출엔 태스크, 도구 어떤거 호출했는지, 그리고 결과, 세번째부터는 그 메세지에 플러스로 또 도구호출, 결과가 계속 쌓임
total 토큰수가 그래서 계속 쌓이는 구조
생기는 비용문제 -> 스텝이 늘어날수록 선형 증가가 아니라 쌓인데 계속 쌓이는 복리형태로 늘어난다. -> 토큰당 비용을 받기 때문에 과도한 사용료, 모델이 받아들일 수 있는 컨텍스트도 한계가 있기 때문에 일정량 넘어가면 압축을해줘야함.

구조 : [task] -> [task, call1, result1] -> [task, call1, result1, call2, result2] -> ... -> [task, call1, result1, ... , callN, resultN]


2. LangGraph를 얹으면 추가되는 것 3가지 / 사라지는 것 1가지 
Langgraph를 얹으면 추가되는 것 : 상태 저장하는 기능 -> 노드들 사이를 공유하는 딕셔너리(state)를 둠, 함수밖에서 분기(컨디셔널 엣지로 이어서 분기), Checkpointer(노드 하나 실행할때마다 상태 저장하는 저장소), interrupt(그래프를 실행 중간에 멈추게 하는 장치)
사라지는것 : 노드랑 엣지간의 연결만으로 표현이 가능해짐 -> 내부적으로 알아서 메세지가 쌓이고, interaction해서 안에 무슨 툴 쓰고 이런 정의도 안해도되고 간단해짐
